# Synthetic PCAP investigations

All four PCAPs are generated by [`scripts/generate_examples.py`](../scripts/generate_examples.py). They contain synthetic packets only; no traffic was captured from a user or network. Addresses, packet order, timestamps, and TLS random bytes are deterministic. The generator uses Python's standard library and writes each record as it is produced.

Build NetScope once with `cargo build --release`. The checked-in files are small classic Ethernet PCAPs: [normal](pcaps/normal.pcap), [port scan](pcaps/port-scan.pcap), [SYN flood](pcaps/syn-flood.pcap), and [protocol edges](pcaps/protocol-edges.pcap). [`pcaps/manifest.json`](pcaps/manifest.json) records packet and wire-byte counts, expected parser accounting, file sizes, and SHA-256 hashes.

Regenerate the checked-in PCAPs with:

```sh
python3 scripts/generate_examples.py
```

Check that the checked-in files match the generator with:

```sh
python3 scripts/generate_examples.py --check
```

The anomaly examples use [`anomaly-demo.toml`](anomaly-demo.toml). Its thresholds are intentionally small and are for these fixtures only; they do not change NetScope's production defaults.

## Normal traffic

**Question:** Can NetScope show the flow, DNS, and packet-level TLS fields in a short ordinary exchange?

```sh
./target/release/netscope --read-pcap examples/pcaps/normal.pcap --config examples/anomaly-demo.toml --no-quiet --summary-json /tmp/netscope-normal-summary.json --export-json /tmp/netscope-normal-flows.json --alerts-jsonl /tmp/netscope-normal-alerts.jsonl
```

The fixture has an IPv4 TCP handshake, a TLS ClientHello and ServerHello, a client ACK, and a DNS A query/response. Look for `TLS ClientHello sni=api.example.test`, `DNS id=0x4242 Q A www.example.test`, and the DNS response with one answer. The flow export should contain one TCP flow with six packets (`packets_a_to_b` = 4, `packets_b_to_a` = 2) and one UDP flow with two packets (one in each direction). The summary reports eight frames and zero alerts.

This shows that a complete ClientHello carried in one packet can expose a visible SNI and that this DNS message can be decoded. The capture ends during the TLS handshake; it does not demonstrate handshake completion, application data, TCP stream reassembly, resolution of a live name, or visibility when TLS ECH hides the server name.

## Port scan heuristic

**Question:** Does one source's burst of probes to distinct TCP ports cross the configured scan threshold?

Inline:

```sh
./target/release/netscope --read-pcap examples/pcaps/port-scan.pcap --config examples/anomaly-demo.toml --quiet --summary-json /tmp/netscope-port-scan-summary.json --alerts-jsonl /tmp/netscope-port-scan-alerts.jsonl
```

Two-worker pipeline:

```sh
./target/release/netscope --read-pcap examples/pcaps/port-scan.pcap --config examples/anomaly-demo.toml --quiet --pipeline --workers 2 --summary-json /tmp/netscope-port-scan-pipeline-summary.json --alerts-jsonl /tmp/netscope-port-scan-pipeline-alerts.jsonl
```

The source sends 16 initial SYNs to one host on distinct ports within the configured 10-second window. The demo threshold is four unique destination ports. With the current per-worker detector, the inline run emits one `port_scan` alert and the two-worker run emits two, one from each shard. `alerts_emitted` in the summary matches the number of JSONL records. A legitimate inventory scan or burst of connection checks can meet the same rule, so this heuristic does not establish intent or malicious activity.

## SYN flood heuristic

**Question:** Does a source-diverse burst of initial SYN packets to one destination and port cross the configured threshold?

Inline:

```sh
./target/release/netscope --read-pcap examples/pcaps/syn-flood.pcap --config examples/anomaly-demo.toml --quiet --summary-json /tmp/netscope-syn-flood-summary.json --alerts-jsonl /tmp/netscope-syn-flood-alerts.jsonl
```

Two-worker pipeline:

```sh
./target/release/netscope --read-pcap examples/pcaps/syn-flood.pcap --config examples/anomaly-demo.toml --quiet --pipeline --workers 2 --summary-json /tmp/netscope-syn-flood-pipeline-summary.json --alerts-jsonl /tmp/netscope-syn-flood-pipeline-alerts.jsonl
```

The trace contains 64 synthetic source addresses targeting `203.0.113.200:443` over 3.15 seconds. The fixture config requires at least eight SYNs and eight unique sources in a five-second window, with a 60-second cooldown. The inline run emits one `syn_flood` alert; the current two-worker pipeline emits one per shard (two total). Pipeline anomaly state is currently per worker, so alert totals can differ by mode. Packet counts and zero dispatch drops are still reconciled in the run summary. Packet-only evidence cannot show whether a server was reachable, how many handshakes completed, or whether a real service was impaired.

## Parser boundary spot-check

Run the supplementary edge fixture with:

```sh
./target/release/netscope --read-pcap examples/pcaps/protocol-edges.pcap --quiet --summary-json /tmp/netscope-protocol-edges-summary.json
```

It contains IPv6 TCP, QinQ-tagged IPv4 UDP, ICMPv4, ICMPv6, a truncated TCP header, and an unsupported EtherType. The expected summary has six frames read, four packets with a transport header, and two malformed or unsupported packets. This checks the listed packet boundaries; it is not exhaustive protocol coverage.
